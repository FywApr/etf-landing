  1. Scope and audience

  The audience is Czech retail investors arriving on mobile from paid ads, who
  know "S&P 500 ETF" as a term but have not compared individual funds.

  In scope
  - One landing page with two entry variants, one per ad.
  - A comparison of 6–8 verified ETFs.
  - A fee calculator.

  - First-party funnel tracking.

  Out of scope: accounts, a CMS, live prices, performance figures, email

  2. Stack

  The stack is unchanged: Next.js App Router, TypeScript, Tailwind, Neon
  Postgres, Zod and Vitest on Vercel. The one addition is @react-pdf/renderer,
  so the guide is generated from the same data file as the page and the two
  cannot drift apart.

  3. Lead magnet

  The offer is "Průvodce americkými ETF pro české investory", a PDF containing:
  - the extended comparison, with more fields per fund than the page shows;
  - an explanation of EU access limits;
  - a practical checklist for choosing an ETF.

  Delivery works without an email service:
  - A successful submission creates the lead with a random guideToken and
    redirects to /dekujeme?t=….
  - The download route checks the token against the database and streams the
    PDF.
  - The PDF is not in public/, so it cannot be fetched without a lead.

  4. Interactive fee calculator

  - Inputs: initial deposit, monthly contribution, horizon in years, assumed
    annual return, and one or two ETFs from the list.
  - Outputs: final value per fund, the amount lost to fees, and the difference
    between the two funds.
  - Formula: shown on the page and implemented as one pure function in
    lib/calculator.ts.
    - i = (1 + r − TER)^(1/12) − 1
    - FV = P(1+i)^n + C·((1+i)^n − 1)/i
    - feeCost = FV(TER=0) − FV(TER)
  - Labelling: the return is a user assumption, not a forecast. The page states
    that the result ignores taxes, FX, broker fees and spreads.
  - Tests: zero return, zero fee, a hand-computed reference value, and fee cost
    rising with TER.

  5. Ads and visitor journey

    gives step-to-step rates.
  - Consent rate: taken from the leads table.
  - Limitation: a reload counts as a new session.

  8. Privacy and validation

  - Validation: the server action validates with Zod, normalises the email, and
    uses a honeypot plus a minimum fill time against spam.
  - Persistence: the lead and lead_created are written in one transaction. On
    failure the visitor sees an error and gets no guide access.
  - Duplicates: a repeat email gets the same response and guide access, without
    revealing that it exists.
  - Two purposes: the email is required for guide access. Marketing is a
    separate, unticked, optional checkbox, stored with a timestamp and the
    consent text version.
  - Controller details: the privacy page reads them from environment variables.
    If they are missing it shows a visible "to be completed" notice, and the
    README lists this as a launch blocker. Nothing is invented.

    exists, and they disappear from historical funnel reports.

  Problems found and fixed

  1. Tokens in URLs. /dekujeme?t=… and /api/guide?token=… exposed the token to
     browser history, request logs and screenshots.
     - The server action now puts the token in an HttpOnly, SameSite=Strict
       cookie and redirects to plain /dekujeme. In production the cookie is also
       Secure and named __Host-guide_access.
     - Both routes read only the cookie; a token in the query string is ignored.
  2. No rate limiting. Added a Postgres-backed limiter for the form, the events
     endpoint and the guide download (details below).
  3. Wrong referrer header on the download. The new global Referrer-Policy
     overrode the route's own no-referrer, because next.config headers win over
     route headers. I found this on the live build and added a route-specific
     rule after the global one.
  4. False database errors on /dekujeme. Next.js aborts I/O when its prerender
     pass ends; the Neon driver wrapped that abort and the page's error handler
     swallowed it, logging two NeonDbErrors per visit. Visitors still saw the
     correct page. The error is now rethrown with unstable_rethrow (also on the
     wrapped sourceError), and the live log is clean.
  5. Missing security headers. Added nosniff, frame denial, a restrictive
     Permissions-Policy, HSTS and a minimal CSP (frame-ancestors, base-uri,
     form-action, object-src). I left out script-src because it would need
     nonces and would break Next.js scripts.
  6. Events endpoint accepted any origin and content type. It now rejects other
     sites' Origin (403) and non-JSON bodies (415).

  Rate limiting

  - How it works: fixed-window counters in a new rate_limits table, shared by
    all server instances, one atomic SQL statement per check.

  | Applies to       | Per client | Global | Window |
  |------------------|------------|--------|--------|
  | Lead form        | 5          | 100    | 10 min |
  | Guide download   | 20         | 300    | 10 min |
  | Analytics events | 120        | 3000   | 1 min  |

  - Per-client limits need Vercel. Vercel's docs state it overwrites
    x-forwarded-for to prevent spoofing. Anywhere else that header can be
    forged, so only the global limits apply, including your local next start.
  - Per-client limits also need RATE_LIMIT_SECRET (not set yet). The IP is never
    stored, only a keyed hash, kept 24 hours. That hash is pseudonymous, not
    anonymous, and the privacy notice says so.
  - Fail-open: if the limiter's database write fails, requests are allowed and
    the failure is logged.
  - Platform layer: Vercel WAF rate limiting is available on all plans, but
    Hobby allows only one rule. A suggested rule is documented for Stage 6; none
    is configured.
